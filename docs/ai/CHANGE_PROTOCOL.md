# Change Protocol

> 用途：规定每次修改如何开始、实施、验证和交接。

## 标准修改流程

```text
收到需求
↓
读取 AGENTS.md、PROJECT_STATE.md、文档导航
↓
检查 Git、真实路径、运行环境和已有修改
↓
读取专项架构、测试、部署/运维文档
↓
定位已有实现、状态机、配置和测试
↓
确定影响范围、数据风险、验证等级和回滚点
↓
实施最小范围修改
↓
运行 L1/L2 相关检查
↓
按风险执行 L3/L4 验证
↓
审查 diff、产物、哈希、数据与配置状态
↓
更新必要文档并输出交接报告
```

## 修改前记录

- 任务目标：{{目标。}}
- 当前分支/commit：{{值。}}
- 用户已有改动：{{文件及处理方式。}}
- 影响模块：{{范围。}}
- 禁止触碰：{{数据、设备、配置。}}
- 计划验证：{{L1-L4。}}
- 回滚点：{{备份、commit 或快照。}}

## 验证分级写法

- L1：静态检查/编译通过，只能证明语法、类型或构建层面成立。
- L2：自动测试通过，只能证明已覆盖场景成立。
- L3：软件运行/集成通过，必须写明环境、输入和观察结果。
- L4：真实环境/硬件通过，必须写明设备、负载、安全状态、日期和证据。

推荐报告句式：

> 已完成 {{范围}} 的 L{{等级}} 验证，证据为 {{证据}}；尚未验证 {{边界}}，因此不能宣称 {{更高等级结论}}。

## 文档更新判定

需要更新长期文档：

- 协议、端口、路径、配置源、启动链或退出链变化；
- 安全状态机、权限、数据保存、备份或恢复策略变化；
- 数据库 schema、外部接口、构建或发布流程变化；
- 测试等级、验收标准或 Source of Truth 变化。

通常不需要更新长期文档：

- 不改变规则的错别字和局部样式；
- 一次性实验或临时诊断日志；
- Git 历史已经足够表达的机械重构。

## 对话/阶段交接

1. 核对真实 Git 和运行状态。
2. 更新 `PROJECT_STATE.md` 与 `TODO.md`。
3. 只有长期决策变化才更新 `DECISIONS.md`。
4. 只有架构事实变化才更新专项架构文档。
5. 用 `templates/CHANGE_RECORD.md` 记录本次证据和未验证边界。
6. 不把聊天全文复制进文档。
