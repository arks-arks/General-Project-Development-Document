# 通用项目开发文档模板

> 用途：把一个项目的规则、现状、设计依据、验证证据和交接信息组织成可持续维护的知识体系。  
> 适用范围：软件、嵌入式、硬件联调、桌面端、Web、AI、数据与混合型项目。  
> 使用方式：复制整个目录到新项目，替换所有 `{{占位符}}`，删除不适用章节。

## 这套模板解决什么问题

- 新成员或新对话不知道先读什么、从哪里改。
- 源码、运行目录、发布产物和实验副本混在一起。
- “代码能编译”“软件能运行”“真实设备通过”被错误地当成同一结论。
- 关键设计只存在于聊天或个人记忆中。
- 发布包误带客户数据、密钥、日志、模型或开发文件。
- 修改完成后没有明确的测试证据、回滚点和未验证边界。

## 推荐目录

```text
项目根目录/
├─ AGENTS.md                         # 人和 AI 都必须遵守的项目规则
├─ PROJECT_STATUS.md                 # 跨仓库、跨设备的项目总状态，可选
└─ docs/
   ├─ README.md                      # 文档导航与职责边界
   ├─ ai/
   │  ├─ PROJECT_STATE.md            # 当前代码库状态
   │  ├─ DECISIONS.md                # 长期设计决策及原因
   │  ├─ TODO.md                     # 仅记录未完成事项
   │  ├─ CHANGE_PROTOCOL.md          # 修改、验证和交接流程
   │  └─ GIT_WORKFLOW.md             # Git、分支和发布治理
   ├─ architecture/
   │  ├─ SYSTEM_ARCHITECTURE.md      # 系统总架构
   │  └─ MODULE_TEMPLATE.md          # 专项模块文档模板
   ├─ deployment/
   │  └─ BUILD_AND_RELEASE.md        # 构建、部署、更新和回滚
   ├─ testing/
   │  └─ TEST_MATRIX.md              # 分层验证矩阵
   ├─ operations/
   │  └─ RUNBOOK.md                  # 运行、诊断、恢复手册
   └─ templates/
      ├─ CHANGE_RECORD.md            # 单次变更记录
      ├─ RELEASE_RECORD.md           # 单次发布记录
      └─ REAL_ENV_TEST_RECORD.md     # 真实环境/硬件验收记录
```

## 最小使用方案

小项目先保留以下 6 份文件即可：

1. `AGENTS.md`
2. `docs/README.md`
3. `docs/ai/PROJECT_STATE.md`
4. `docs/ai/DECISIONS.md`
5. `docs/ai/TODO.md`
6. `docs/testing/TEST_MATRIX.md`

当项目出现部署、客户数据、外部设备、安全状态机或多人协作时，再启用其余文档。

## 文档职责原则

| 信息 | 唯一归属 | 不应放在哪里 |
|---|---|---|
| 必须遵守的规则 | `AGENTS.md` | 状态日志、聊天记录 |
| 项目现在是什么状态 | `PROJECT_STATE.md` | `DECISIONS.md` |
| 为什么这样设计 | `DECISIONS.md` | `TODO.md` |
| 还没完成什么 | `TODO.md` | 已完成记录 |
| 系统如何连接和运行 | `architecture/` | 超长状态日志 |
| 修改后测什么 | `TEST_MATRIX.md` | 仅靠口头约定 |
| 如何构建、部署、回滚 | `BUILD_AND_RELEASE.md` | 零散脚本注释 |
| 单次变更证据 | `templates/CHANGE_RECORD.md` 的实例 | 长期架构文档 |

同一事实只维护一份，其他文档用相对路径引用。

## 建议的事实优先级

```text
当前磁盘源码与真实设备状态
↓
Git 状态、diff、配置、构建脚本和自动测试
↓
当前有效项目文档
↓
发布记录和历史文档
↓
聊天记录与个人记忆
```

文档与源码冲突时，先核对真实实现，再更新或标记过时文档，不能为了“文档一致”反向猜测代码。

## 推荐验证等级

| 等级 | 含义 | 典型证据 |
|---|---|---|
| L1 | 静态检查/编译 | lint、类型检查、语法检查、编译日志 |
| L2 | 自动测试 | 单元、组件、契约、回归测试 |
| L3 | 软件运行/集成 | 应用启动、页面交互、服务联调、模拟环境 |
| L4 | 真实环境/真实硬件 | 现场设备、生产依赖、真实负载和故障注入 |

高等级不会自动覆盖所有低等级；报告必须写明“通过了什么”和“没有验证什么”。

## 初始化步骤

1. 复制本模板目录到新项目。
2. 全局搜索 `{{`，替换占位符。
3. 在 `AGENTS.md` 写清唯一源码目录、禁止修改范围和高风险规则。
4. 在 `PROJECT_STATE.md` 记录真实版本、分支、运行基线和已知风险。
5. 在 `docs/README.md` 建立任务到文档的导航。
6. 根据实际模块复制 `MODULE_TEMPLATE.md`。
7. 删除不适用内容，不保留虚假“已完成”项。
8. 首次提交前检查所有文本为 UTF-8，并确认不包含密钥、客户数据和本机隐私路径。

## 维护节奏

- 每次任务前：读规则、状态、专项文档，检查 Git 和真实路径。
- 每次任务后：记录改动、测试等级、未验证边界和回滚点。
- 阶段完成时：更新 `PROJECT_STATE.md` 与 `TODO.md`。
- 只有长期决策变化时：更新 `DECISIONS.md`。
- 只有架构事实变化时：更新对应架构文档。
- 发布时：生成独立发布记录，不把整段聊天复制进长期文档。
